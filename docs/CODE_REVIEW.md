# Codebase Review — Reproducibility Audit of `docs/JOURNAL.md`

**Scope:** entire repository (`src/stillwar`, `tests`, `configs`, `Makefile`, `pyproject.toml`, committed artifacts, git history).
**Lens:** software-engineering architecture and structure, judged by one criterion — *can a third party regenerate every number, table and figure in the manuscript from a clean checkout?*
**Date:** 8 November 2026 · **Version reviewed:** `1.0.0` (HEAD `05c29a3`)

---

## 0. Executive verdict

The **scientific core is sound and unusually well engineered for a single-author paper**: the vectorised order-2 log-signature, the multiplier-free KKT test, the Ledoit–Wolf estimator, the purged/embargoed split logic, and the SLSQP formulation are each correct, compact and directly traceable to an equation in the manuscript. Theorem 1 is verified against the numerical solver by property tests that genuinely test the property.

The **reproducibility layer is not sound.** The repository is currently a *collection of artifacts plus code that can read them*, not a pipeline that regenerates them. Concretely:

| Question | Answer |
|:---|:---|
| Does `make all` work on a clean checkout? | **No** — fails at `simulate` (missing input, no producer). |
| Does the committed `table1_results.json` match Table 1 of the manuscript? | **No** — 2 of 18 rows disagree. |
| Are the figures generated from the experiment results? | **No** — Figure 4 is 100% hardcoded literals. |
| Is the Deflated Sharpe ratio computed from the 1,235 trials the paper claims? | **No** — the trial distribution is a hardcoded `rng.normal(0.722, 0.327, 1235)`. |
| Do the tests validate the code that produced the paper's numbers? | **Partly** — the production feature path and the training path are untested; 4 tests depend on git-ignored artifacts. |
| Can a result JSON be traced to the config that produced it? | **No** — `Config.digest` exists but is never written anywhere. |

**Verdict: not reproducible in its current state; the gap is architectural, not mathematical.** Roughly 80% of the defect surface is concentrated in two modules — `reporting.py` (593 LOC) and `__main__.py` (210 LOC) — and in the absence of a table renderer. The remediation is well-scoped and does not require re-running training.

---

## 1. Method

1. Read `docs/JOURNAL.md` end-to-end and extracted every quantitative claim (tables, figures, inline statistics).
2. Read all 13 source modules and all 8 test modules.
3. Cross-referenced each claim against its producing code path and its committed artifact in `data/processed/` and `reports/figures/`.
4. Ran the test suite (`31 passed in 22.67s`) and inspected the committed artifacts and git state.
5. Ran static symbol-usage analysis to classify every public function as *used by pipeline*, *used only by tests*, or *dead*.

## 2. Blocking defects (P0) — these invalidate the reproducibility claim today

### B1. `make all` cannot succeed from a clean checkout

`Makefile:22`

```make
all: verify features simulate experiments figures test
```

Three independent breaks:

1. **`train` is not in the chain.** `simulate` immediately does `np.load("data/processed/forecasts_logsig.npz")` (`__main__.py:100`), which only `stage_train` writes. On a clean clone this is a `FileNotFoundError`.
2. **`forecasts_baselines.npz` has no producer anywhere in the repository.** `__main__.py:102` reads it; a full-tree grep for the string finds only that read plus three test reads. It cannot be regenerated by any command. It is also git-ignored (`data/processed/*.npz`), so it is absent from a clone. This single file supplies the MLP, LSTM, Hist-MV and GMV forecasts that populate **7 of the 9 rows of Table 1** and all of Table 2's `ψ⁰` column.
3. **`test` is in the chain but depends on git-ignored artifacts.** `test_forecast_arrays_integrity`, `test_hist_mv_shrinkage_calculation`, `test_logsig_forecasts_npz`, `test_logsig_inc_forecasts_npz` all require `*.npz` that `make all` never produces.

**Manuscript claim contradicted:** §2.10 — *"one command, `make all`, regenerates every table and figure from it"*.

### B2. Table 1 disagrees with the committed artifact

`data/processed/table1_results.json` vs `docs/JOURNAL.md` lines 159 and 169:

| Row | Manuscript | Committed JSON | Match |
|:---|:---|:---|:---:|

| Hist-MV, unpenalized (Panel B) | 11.38% / 0.32 / 30.24% / 45.37% / +12.03% (t=1.12) / 0.1161 | 12.11% / 0.34 / 30.24% / 45.36% / +12.69% (t=1.18) / 0.1245 | ❌ |

The other 16 rows match exactly. The divergence propagates into the prose: §3.6 states *"Unpenalized Hist-MV records the highest raw net CAGR and Sharpe ratio in both Panel A (29.34%, Sharpe 0.95) and Panel B (11.38%, Sharpe 0.32)"* — the artifact says 30.51%/0.99 and 12.11%/0.34.

**Why the test suite does not catch it:** `test_reporting_consistency.py::test_tables_and_manuscript_reconciliation` asserts only the `κ = 5 (primary)` row of Table 2 and the `LogSig` Panel A row of Table 1. It is a spot-check, not a reconciliation.

**Root cause:** there is no table renderer. The Markdown tables in `JOURNAL.md` are hand-transcribed from JSON by a human. Any regeneration silently desynchronises the manuscript, and nothing detects it. This is the single most important structural defect in the repository.

### B3. The Deflated Sharpe ratio is not computed from the trials the paper claims

`reporting.py:65-66`

```python
rng = np.random.default_rng(42)
trial_sharpes = rng.normal(0.722, 0.327, 1235)
```

The manuscript (§2.10) states: *"We count M = 1,235 trials. The sensitivity grid crosses γ ∈ {1,2.5,5,10}, κ ∈ {0,1,2.5,5,10} and a cost multiplier m ∈ {0.5,1,2} … for four models and five seeds (1,200 trials)"*.

**No such grid exists in the codebase.** The largest grid actually run is `generate_table2`'s 11 configurations × 5 seeds = 55 backtests of LogSig only. The 4×5×3×5 = 300-cell, 1,200-run grid that the paper describes as the basis of `M` is absent. The `0.722` and `0.327` are unexplained literals; only the variance enters `deflated_sharpe` (`stats.py:62`), so the entire DSR column of Table 1 — including the headline `0.0854` for LogSig — is a fixed constant plugged into a formula, not a measurement.

This is the most serious *scientific* reproducibility defect: the DSR is the paper's defence against backtest overfitting, and it is currently unfalsifiable from the repository.

### B5. Training artifacts are orphaned — the tests validate the wrong models

`stage_train` writes (`__main__.py:67` → `train.py:167`):

```
models/checkpoints/logsig/logsig_seed_{0..4}.pt
models/checkpoints/logsig_inc/logsig_inc_seed_{0..4}.pt
models/checkpoints/mlp/mlp_seed_{0..4}.pt
models/checkpoints/lstm/lstm_seed_{0..4}.pt
```

What is actually committed, and what the tests load:

```
models/checkpoints/logsig/msgn_seed_{0..4}.pt          ← tests expect this
models/checkpoints/baselines/mlp_seed_{0..4}.pt        ← tests expect this
models/checkpoints/baselines/lstm_seed_{0..4}.pt       ← tests expect this
models/checkpoints/logsig_inc/logsig_inc_seed_{0..4}.pt ← matches
```

Consequences:

1. `make train` produces a directory tree that **no test reads**. The test suite will pass while validating stale committed checkpoints, so a training regression is undetectable.
2. The MLP and LSTM forecasts are **never saved by any code path**. `stage_train` has explicit `if model_name == "logsig"` / `elif model_name == "logsig_inc"` branches only (`__main__.py:69-92`). The MLP/LSTM rows of Table 1 therefore depend on `forecasts_baselines.npz`, which (B1) has no producer.
3. `test_logsig.py:23` asserts `data["lr"] == 1e-3`, but `select_best_lr` (`train.py:111`) chooses between `1e-3` and `3e-4` for `logsig` and `mlp`. The test hardcodes the *outcome* of a hyperparameter search. If `3e-4` wins on a re-run, the test fails for a correct reason.

### B6. The production feature path is untested; the leakage test tests a different implementation

Two implementations of the same mathematics coexist in `features.py`:

| Function | Used by production? | Tested? |
|:---|:---:|:---:|
| `logsig_features` (vectorised, line 18) | **Yes** — `build_dataset:141` | **No** |
| `compute_order2_logsig_for_windows` (scalar reference, line 51) | No | Yes — 3 tests |
| `compute_increments_and_levy_areas` (line 40) | Only by the scalar reference | Yes — 4 tests |

`test_no_leakage.py::test_feature_strict_historical_window` — the repository's zero-look-ahead guarantee — exercises `compute_order2_logsig_for_windows`, which **never runs in the pipeline**. There is no test asserting `logsig_features(x, (5,20,60))[t] == compute_order2_logsig_for_windows(x, t)`. The vectorised path, with its cumulative-sum trick, stride arithmetic and `np.nan_to_num(path - np.nanmean(path, axis=0))` normalisation, has **zero** direct coverage.

Compounding this, `test_no_leakage.py::test_target_execution_lag` is a tautology — it defines a local `compute_target` that discards its first argument and then asserts the first argument does not matter:

```python
def compute_target(p_decision, p_exec, p_exit):
    _ = p_decision
    return float(np.log(p_exit / p_exec))
```

It tests no code in `stillwar`. It creates a false sense of coverage on the single most important correctness property in the paper (the `t+1` execution lag).

## 3. Architectural inefficiencies

### A1. `run_backtest` is a god function

`portfolio.py:224-409` — 186 lines, 6 positional parameters, `**kwargs`, and a 17-key return dict. It simultaneously owns: price→return conversion, covariance estimation, forecast shrinkage, KKT evaluation, QP dispatch, short-circuiting, drift propagation, cost accounting, daily P&L accumulation, metric aggregation, and KKT logging.

The parameter handling is the worst part:

```python
def run_backtest(prices, dates, tickers, forecasts=None, cfg: Trading | Config | None = None, **kwargs): ...
def get_param(name, default):
    if name in kwargs: return kwargs[name]
    return getattr(tr, name, default) if tr is not None else default
```

`get_param` **duplicates every default from `configs/base.yaml` as a literal** (`0.0015`, `0.0025`, `5.0`, `2.5`, `0.15`, `0.5`, `5`, `60`, `0.06`, `1e-4`, `1e-6`, `True`, `False`, `True`). This is not a convenience — it is an active correctness hazard, and it has already fired:

`reporting.py:227-240` (`_eval_t2_task`) passes only `c_b, c_s, kappa, gamma, log_forecast`. Every other parameter silently falls back to the literal default. Table 2 is therefore **not** controlled by `base.yaml`; it is controlled by `portfolio.py`'s hardcoded literals. Change `w_max` in the config and Table 2 will not move, while Table 1 will. The two tables would then describe different strategies under the same caption.

The union type `Trading | Config | None` is also a leaky abstraction: the backtest engine knows the schema of the configuration object, so `portfolio.py` (the mathematical core) cannot be reused or unit-tested without `config.py`.

### A2. No memoisation — the same deterministic backtest is recomputed at least 9 times

A backtest is a pure function of `(prices, dates, tickers, forecasts, params)`. It is never cached. The primary configuration (LogSig, seed 0, κ=5, Panel B) is recomputed by:

| Call site | Purpose |
|:---|:---|
| `reporting.py:134` (`_eval_t1_task`, task 0) | Table 1 |
| `reporting.py:221` (`tabulate_kkt_agreement`) | Table 3 — reuses the same object ✅ |
| `reporting.py:291` (`generate_table2`, κ=5 primary, seed 0) | Table 2 |
| `reporting.py:325` (`generate_phase4_diagnostics`, `res_k5_s0`) | declined-trade counterfactual |
| `reporting.py:369` (`tau_ls` loop, seed 0) | turnover mean |
| `reporting.py:312` (`run_volatility_penalty_experiment`, uniform, seed 0) | Table S1 |
| `reporting.py:163` (`plot_figure2` via `stage_figures`) | Figure 3 |
| `reporting.py:406-490` (`plot_figure1`, own loop) | Figure 2 |
| `experiments.py:172` (α=0.50, seed 0) | Figure 4B |
| `experiments.py:38` (w_max=0.15, eps=0.0, seed 0) | Figure 4A |

Each run is 128 SLSQP solves of a 120-variable QP plus 128 Ledoit–Wolf 40×40 estimates. Total pipeline cost is roughly 200 full backtests, of which ~9 are byte-identical duplicates of the most expensive object. A single `functools.lru_cache` keyed on a hash of the inputs would remove them.

### A3. `plot_figure1` is a second, divergent implementation of the simulation

`reporting.py:406-490` re-implements the entire rebalance/drift loop from scratch: covariance estimation, forecast shrinkage, gradient computation, `J`/`I` set construction, QP call, drift propagation, holding-window iteration. ~85 lines duplicating `run_backtest`.

It also hardcodes what `run_backtest` reads from config:

```python
elif dg > 0.020:                                                    # line 445 — band literal
w_opt, to = solve_qp(..., 0.0075, 0.0125, w_max=cfg.trading.w_max)  # line 450 — η literals
w_holding = w_opt.copy() if to > 1e-4 else w_drift.copy()           # line 455 — τ literal
```

This matters because **Figure 2 and Table 3 are supposed to be two views of the same fact.** Table 3 comes from `run_backtest`'s `kkt_logs`; Figure 2 comes from this duplicate loop. If the two ever diverge, the manuscript's central claim ("100% agreement, 26 trades / 13 holds") would be internally inconsistent with its own figure — and nothing would catch it.

The duplication is entirely unnecessary. `run_backtest` already returns `kkt_logs` with `date`, `delta_g`, `threshold`, `is_cap_drift`, `kkt_should_trade`, `trigger_sell_idx`, `trigger_buy_idx` — everything `plot_figure1` needs. The function could be ~15 lines reading `kkt_logs` instead of ~85 lines re-simulating.

### A4. Three near-identical process-pool wrappers

```python
experiments.py:17   _eval_exp_task(close_df, dates_b, tickers, fc, kw)          → run_backtest(..., **kw)
reporting.py:26     _eval_t1_task(close_df, dates_b, tickers, fc, tr_dict, kap, is_log) → run_backtest(..., 12 named kwargs)
reporting.py:227    _eval_t2_task(close_df, fc, dates_prefix, tickers, cutoff_a, cb, cs, kap, gam, is_log) → run_backtest(..., 6 kwargs)
```

Three different conventions for the same job: one passes a dict, one enumerates 12 parameters, one enumerates 6. The positional-tuple protocol is fragile (adding a parameter means editing three call sites and three tuple constructions) and untyped. All three exist because `run_backtest` has no serialisable parameter object.

### A5. Results are stored as pre-formatted strings

`reporting.py:174-190`:

```python
"cagr":     f"{np.mean(cagrs_a) * 100:.2f}% ± {np.std(cagrs_a) * 100:.2f}%",
"sharpe":   f"{np.mean(shs_a):.2f} ± {np.std(shs_a):.2f}",
"nw_alpha": f"{alpha_a * 100:+.2f}% (t={t_a:.2f})",
```

The JSON artifacts are therefore **not machine-readable results** — they are rendered strings. Consumers can only substring-match (`test_reporting_consistency.py:79`: `assert t1["LogSig"]["panel_a"]["cagr"].startswith("25.10%")`). Consequences:

- Numeric precision is destroyed at write time; downstream recomputation, rounding checks, and significance tests are impossible.
- The same defect appears in `experiments.py:324-334`, where `cagr`/`sharpe`/`mdd`/`turnover` are written as `"8.58%"` strings while the sibling fields in the same dict are floats.
- It is why B2 slipped through: a string field cannot be compared to a manuscript cell without a human.

### A6. No provenance in any artifact

`config.digest` (`config.py:89-91`) is defined and **never called**. No artifact records the config digest, git SHA, or dependency versions. `data/processed/metadata.json` — itself an orphan (see A8) — records `start_date`, `n_dates`, and dimension counts, but nothing that identifies *which configuration* produced it.

A reviewer cannot answer "was `table1_results.json` produced by `base.yaml` at HEAD?" without guessing. This is the mechanism by which B2 and B4 became possible.

### A7. Dimensional conflation in `slice_panel_a`

`portfolio.py:195-221`:

```python
def slice_panel_a(backtest_result, cutoff_days, cutoff_rebalances=94, ...):
    rets_a = backtest_result["daily_returns"][:cutoff_days]
    tos_a  = backtest_result["executed_turnovers"][:cutoff_rebalances]
```

Callers pass `cutoff_days = len(dates_a)` — a **decision-date count** (467) — to slice a **daily-return array** (~470 entries for 94 cycles), while `cutoff_rebalances = 94` slices a **rebalance array**. Two different units, one function, no validation.

Because `rebalance_freq = 5`, each cycle appends exactly 5 daily returns, so `[:467]` covers 93.4 of 94 cycles. The result is that Panel A's CAGR/Sharpe/MDD are computed over a window that ends **3 trading days before** the window its turnover statistic covers. Small, but it is exactly the kind of silent inconsistency that a reviewer will find and that the code cannot detect.

The function should take a single `n_cycles` argument and derive both slices from it.

### A9. Off-by-one in the tolerance-grid percentages

`experiments.py:102`:

```python
n_dates = len(dates_b) // cfg.trading.rebalance_freq     # 638 // 5 = 127
```

The actual number of rebalance dates is `len(range(0, 638, 5)) = 128`. Every `pct_mean` in `exp_unconstrained_tolerance.json` is therefore divided by 127 instead of 128 — e.g. baseline cap-drift is written as `71.02%` where the correct value is `70.31%`. The manuscript happens to report raw counts (90.2 / 32.0 / …) rather than these percentages, so the error is currently latent — but it is a real defect in a committed artifact, and it is the reason Figure 4A's hardcoded `70.5` (which uses 128) disagrees with the JSON's `71.02` (which uses 127).

### A10. Serial/parallel inconsistency

`experiments.py:41, 81, 176, 230` and `reporting.py:133, 289` use `ProcessPoolExecutor`. But:

- `experiments.py:311-315` runs 10 backtests **serially** in a loop.
- `reporting.py:369-370` runs 10 backtests **serially** inside a list comprehension.
- `reporting.py:325-326, 367` run 3 backtests serially.

On a 5-seed × 2-strategy loop that is the difference between ~1 minute and ~10 minutes of wall clock, for no reason other than that these call sites were written after the parallel ones.

### A11. `select_best_lr` makes the five seeds non-exchangeable

`train.py:111-128` trains seed 0 once per candidate learning rate, picks the winner on validation, and then `train_model_seeds` re-trains **all five seeds including seed 0** with the winner. Seed 0 is therefore a *selected* model while seeds 1–4 are not. The reported `± s.d.` across five seeds (§3.1, Table 1) understates true seed dispersion, and the "five pinned seeds" framing implies exchangeability that the procedure does not deliver. The fix is either to select the LR on a held-out seed that is excluded from reporting, or to report the LR-selection cost honestly.

### A12. `solve_qp` has a silent-failure path

`portfolio.py:154-162`:

```python
if not res.success and "Iteration limit" not in res.message:
    res = minimize(fun=obj, x0=x0, method="SLSQP", bounds=bounds,
                   constraints=constraints, options={"ftol": solver_tol, "maxiter": 300, ...})
```

Two problems: the retry **drops `jac=obj_grad`**, silently switching to finite differences (slower, less accurate, and a different numerical object than the primary path); and `res.success` is never checked after the retry, so a failed solve is silently accepted and its `res.x` used as the portfolio.

Immediately after (`portfolio.py:164-167`):

```python
w_opt = np.clip(res.x[:n], 0.0, w_max)
s = float(np.sum(w_opt))
if s > 0.0: w_opt = w_opt / s
```

Renormalising *after* clipping can push a weight above `w_max` (if `s < 1`). The magnitude is negligible under normal convergence (`s ≈ 1 ± 1e-12`), but the pattern is dangerous: it is a silent correctness patch that masks solver failure instead of surfacing it.

### A13. The over-broad dataset cache

`features.py:162-170`:

```python
@cache
def _dataset(key: str) -> Dataset:
    cfg = Config.model_validate_json(key)

def load_dataset(cfg): return _dataset(cfg.model_dump_json())
```

The cache key is the **entire** config, but the docstring correctly notes features depend only on `data`, `splits`, and `features`. Any `trading.*` override — e.g. every call inside `experiments.py` — produces a cache miss and a full rebuild of the 45-feature tensor. Conversely, `data.py:102-104` uses a *different* idiom for the same job (`Config.model_construct(data=...)`, bypassing validation). Two caching strategies, two key-derivation schemes, one comment claiming something neither implements.

### A14. `reporting.py` mixes three concerns in 593 lines

The module contains: metric computation (`generate_table1_and_table3`, 185 lines), sensitivity grids (`generate_table2`), counterfactual diagnostics (`generate_phase4_diagnostics`, 90 lines), and Matplotlib rendering (`plot_figure1/2/3`, 187 lines). It is the largest module in the repository and the one with the most defects (B2, B3, B4, A3, A7 all live here or are caused by it).

The structural problem is that **computation and presentation are interleaved**: `generate_table1_and_table3` computes a Sharpe ratio and immediately formats it as `f"{x:.2f}"`; `plot_figure1` computes a backtest and immediately draws it. There is no layer at which a result exists as a number that both a table and a figure can consume.

## 6. What is genuinely good

Worth stating explicitly, so the remediation does not disturb it:

- **`features.logsig_features`** is an elegant piece of numerical work. The identity `Σ_k (x_k − x_0)ⁱ Δx_kʲ = dS_ij − x_0ⁱ (x_W − x_0)ʲ` reduces the ten Lévy areas to one `cumsum` over an `einsum`, making the whole 45-feature tensor a handful of vectorised operations. Correct, fast, and directly traceable to Eq. (1).
- **`portfolio.evaluate_kkt`** is a faithful, compact implementation of Theorem 1, including the generalisation to asset-specific `η` via the pairwise margin matrix with the `j = i` diagonal excluded. The equivalence to `max_J g − min_I g ≤ η_b + η_s` under uniform `η` is exact.
- **`portfolio.ledoit_wolf_covariance`** implements the analytical LW(2004) shrinkage correctly, with a sensible `gamma_hat → 0` guard.
- **`features._split_indices`** is a clean, declarative implementation of purge + embargo, and it *is* exercised by a test (via `split_and_standardize_datasets`), even though that wrapper is otherwise vestigial.
- **`models.py`** is exemplary: 102 lines, four architectures, parameter counts that match the manuscript exactly (923 / 353 / 1,505 / 4,513 — verified by tests), and no configuration coupling.
- **`config.py`** is a good idea (frozen Pydantic, `extra="forbid"`, dotted overrides, content hash). It is under-used rather than wrong.
- **`test_kkt_theorem.py`** tests the actual mathematical claim (analytical verdict vs. numerical solver) on random instances, including the vector-`η` case. This is the right kind of test.
- The **raw-data SHA-256 manifest** and the `_sha256` CRLF normalisation are a thoughtful touch, and `_load_panel` verifies on every cache miss.
